# SQNR web app

The Spatial Capture web app as a static single-page app: TanStack Router (file-based routes) and TanStack Query, built with Vite, talking only to the Spatial Capture API. The API, worker and database live in the platform repo ([SQNR-new](https://github.com/nishants1-damco/SQNR-new)); the migration plan is `docs/architecture/scaling-migration-plan.md` there (§13, phase 4).

**Status: phase 4 (frontend migration).** Every route from the original app runs on the API: sign-in (plus email verification and password reset), the catalog, the space page, and capture with reshoots. No Supabase or TanStack Start code remains. What moved and what changed is in [docs/porting-ledger.md](docs/porting-ledger.md).

## Layout

```
src/
  api/          the API layer: client (sessions), auth provider, typed calls,
                Query hooks, direct-to-Blob uploads, analysis runner
  routes/       file-based routes (routeTree.gen.ts is generated by the Vite plugin)
  components/   UI components and shadcn/ui primitives (components/ui)
  hooks/        useFlag, useLeaveGuard
  lib/          browser libraries: acoustics probe, motion tracking, capture drafts...
packages/
  contracts/    @spatial/contracts — API wire schemas   } vendored from the platform
  domain/       @spatial/domain — pure capture logic     } repo; see "Shared packages"
public/         manifest, icons, service worker
e2e/            browser smoke test against a running stack
```

## Getting started

Prerequisites: Node.js 24 (`.nvmrc`), pnpm 12.8.1 (`corepack enable pnpm`), and the platform repo's local stack running with its API and worker (`pnpm infra:up`, `pnpm db:migrate`, `pnpm dev` in the platform repo).

```sh
pnpm install
cp .env.example .env
pnpm dev              # http://localhost:5173, with /v1 proxied to the API on :3000
```

The dev server proxies `/v1` to the API, so the app and the API share an origin exactly as they will behind Front Door: the refresh cookie (scoped to `/v1/auth`) and the event stream need no CORS.

```sh

```

## How it talks to the API

- **Sessions** (`src/api/client.ts`, `auth.tsx`). The access token lives in memory; the refresh token is an HttpOnly cookie the app never sees. The client refreshes shortly before expiry and once on a 401. Refresh tokens rotate and the API treats a replayed one as theft, so refreshes never overlap: one at a time per tab (a shared promise) and across tabs (a Web Lock). Signing out in one tab signs out the others. Requests made before the session has been restored wait for the restore. `useAuth()` keeps the `{ session, user, loading }` shape the routes used with Supabase.
- **Data** (`src/api/spaces.ts`, `queries.ts`). Typed calls per endpoint, typed with `@spatial/contracts`, and Query hooks with the original query keys (`spaces`, `space`, `space-export`). The catalog is a cursor-paginated infinite query with search, filter and sort on the server. The space page is one request instead of five.
- **Uploads** (`src/api/uploads.ts`). Ask the API for create-only upload URLs, PUT the files straight to Blob Storage (four at a time, with retries; a 409 on a retry means the earlier attempt landed), then `complete`. Reshoots pass `replaceStations`, so the new frames and the removal of the old ones commit together on the server.
- **Analysis** (`src/api/analysis.ts`, `useAnalysisRun.ts`). `POST` queues the run in the worker; the app follows it over the SSE stream (read with `fetch`, since `EventSource` can't send the bearer token) and falls back to polling. Leaving the page no longer interrupts a run.

## Shared packages

`@spatial/contracts` and `@spatial/domain` are the same code the API and worker use. They are vendored under `packages/` unchanged, as source (Vite and Vitest compile them). The platform repo is the source of truth:

1. Change them there.
2. `pnpm shared:sync` here (looks for `../spatial-capture-platform`, or `SPATIAL_PLATFORM_DIR`).
3. Commit `packages/` together with `packages/shared.lock.json`, which records the platform commit.

`pnpm shared:check` (part of `pnpm check` and CI) fails if a vendored file was edited here.

## Build and hosting

`pnpm build` writes a static site to `dist/`: hashed assets, `index.html`, and `staticwebapp.config.json` for Azure Static Web Apps (SPA fallback, long-lived caching for hashed assets, no caching for `index.html` and the service worker, security headers). The Content-Security-Policy is generated from the build settings and sent both as that header and as a meta tag:

| Variable                | Build-time setting                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| `VITE_API_BASE_URL`     | The API origin; empty when the API is served from the same origin                               |
| `VITE_BLOB_ORIGIN`      | The Blob Storage endpoint. Required: uploads and frame images are blocked by the CSP without it |
| `VITE_API_PROXY_TARGET` | Dev server only: where `/v1` is proxied                                                         |

No secrets belong in these: every `VITE_` value ends up in the browser bundle. The API must list the app's origin in `WEB_ORIGINS` (CORS, and the refresh cookie is refused from any other origin).

The service worker (`public/sw.js`) caches only the app shell and static assets; it never caches `/v1/*` or signed Blob URLs.

## Testing

- `pnpm test`: the API layer (session refresh, error envelope, uploads, the event stream and polling fallback) and the browser libraries ported from the original app (acoustics probe combining, frame quality).
- `pnpm e2e`: signs up in a real Chrome or Edge, uploads a capture's frames to Blob Storage, runs the analysis, checks the catalog, the space page (plan, frames, export), re-running from the page, the privacy sweep, a reload keeping the session, deletes, and sign-out. Works against `pnpm dev` and `pnpm preview`.
